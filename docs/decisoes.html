01 / FRONT-END

Análise léxica e sintática

DecisãoAlternativa consideradaPor que escolhemosConsequência
Blocos por indentação: o lexer gera INDENT / DEDENT com uma pilha de níveis de recuoExigir { } nos blocos (versão usada até a P2)É assim que Python funciona: um programa Python real compila sem adaptação. O parser continua simples, porque enxerga INDENT/DEDENT como se fossem {/}O lexer ficou mais complexo (pilha + fila de tokens pendentes). Recuo inconsistente vira erro léxico
Aspas simples convertidas para duplas no lexer ('oi' → "oi")Converter só na geração de códigoEm Python as duas são iguais; em C, texto só existe com aspas duplas. Normalizando cedo, nenhuma etapa seguinte precisa tratar os dois casosUma " dentro do texto é escapada (\"). A AST mostra sempre aspas duplas
String termina na mesma linha; aspa sem fechamento é erro léxicoAceitar string atravessando linhasUma aspa esquecida fazia o lexer engolir várias linhas até a próxima ", e o erro aparecia longe da causaMensagem com o número da linha exata
Precedência com %left/%right, igual à de Python: or < and < not < comparações < + - < * / % < - unário. Else pendente com %nonassocReescrever a gramática em níveis (expr / termo / fator)Mais curto e legível; é o mecanismo do próprio Bison para isso. Seguir a ordem do Python faz o programa significar o mesmo nas duas linguagens1 + 2 * 3 vira (1 + (2 * 3)); not x == 3 é not (x == 3)
elif vira um if dentro do elseNó próprio de elif na ASTif a: … elif b: … else: … significa exatamente if a: … else: (if b: … else: …). Reaproveita o nó de if e a geração de C já existenteAceita quantos elif forem necessários; o C gerado fica else { if … }
Número negativo literal vira o próprio literal (-5); negativo de expressão vira (0 - x)Nó próprio de “menos unário” na ASTNão precisa de nó novo, e o caso mais comum (x = -5) gera o C mais limpo possível3 - -2, -x * 2 e -(1 + 2) funcionam (PR #49)

02 / SEMÂNTICA

Tipos e verificações

DecisãoAlternativa consideradaPor que escolhemosConsequência
Tipo da variável deduzido pelo primeiro valor atribuído (x = 2.5 → FLOAT)Exigir anotação de tipo (x: float = 2.5) ou usar tipo dinâmico em C (union + etiqueta)Python não declara tipos, mas C exige. A dedução mantém o código Python intacto e gera C simples, com tipos nativosUma variável fica presa ao tipo do primeiro valor
Mudar o tipo de uma variável (x = 10 e depois x = "texto") é erro semânticoPermitir, como Python permiteEm C uma variável tem um único tipo. Aceitar exigiria tipo dinâmico em tempo de execuçãoMensagem: variavel 'x' e inteiro e nao pode receber string
Reatribuição com o mesmo tipo (x = 10 e depois x = 20) é permitidaTratar como redeclaração (erro)É reatribuição válida em Python; não existe “declarar” uma variávelTeste tabela/redeclaracao garante esse comportamento
Usar uma variável antes de atribuir é erro semânticoInicializar com zero automaticamenteEm Python isso é NameError; detectar na compilação é mais útil que um valor silenciosoMensagem: variavel 'x' usada antes de ser definida
and/or/not exigem boolean; % só entre inteirosAceitar qualquer tipo, como Python (truthiness) / % com float via fmodMesma regra já usada nas condições do if/while. % com float exigiria outra função em C para um caso rarox = 1 and 2 e 7.5 % 2 são erros semânticos com mensagem clara
Com qualquer erro semântico, o C não é geradoGerar mesmo assim e deixar o GCC reclamarOs erros do GCC sobre código gerado não fazem sentido para quem escreveu PythonO usuário vê só a mensagem do nosso compilador

03 / BACK-END

Geração de código C

DecisãoAlternativa consideradaPor que escolhemosConsequência
Gerar C direto da AST, sem código intermediário (TAC)AST → TAC → CNo subconjunto escolhido a AST já tem toda a informação necessária, e cada nó vira uma construção C equivalente. Menos código para manter e verificarOtimizações (constant folding, código morto) não foram implementadas; ficariam mais naturais sobre um TAC
Variáveis declaradas no início da função, com o tipo deduzido. Globais lidas por alguma função são declaradas fora do mainDeclarar no ponto do primeiro uso / todas as globais dentro do mainUma atribuição dentro de if ou while declararia a variável só dentro daquele bloco em C. E uma global declarada dentro do main não é visível para as funçõesO gerador percorre a AST antes de emitir: coleta as variáveis e marca quais globais cada função lê
print vira printf com o formato escolhido pelo tipo (%d, %g, %s; booleano impresso como True/False)Um único printf("%d")A saída do programa C fica igual à do PythonO gerador precisa saber o tipo de cada expressão, inclusive de variáveis (PR #41) e do resultado de funções (PR #48)
% via função auxiliar py_resto(), emitida só quando usadaUsar o % do C diretoEm C, -7 % 3 é -1; em Python é 2 (o resto tem o sinal do divisor). A função corrige o sinalO nome py_resto evita colidir com uma variável chamada resto (PR #49)
Float impresso por py_print_float(), que segue o repr do Python; literais escritos com a menor quantidade de dígitos que representa o valor exatoprintf("%g") (versão anterior)%g imprime 2 em vez de 2.0 e guarda só 6 dígitos: o literal 3.14159265 virava 3.14159 no C, ou seja, o valor mudavaSaída igual à do Python (2.0, 0.30000000000000004, 1e+16). Fica visível que uma função C tem um tipo só: se dobro(x) recebe 3 e 2.5, dobro(3) devolve 6.0 (PR #50)
Concatenação de strings via função auxiliar concatenar(), emitida só quando usadaUsar strcat direto no ponto do +strcat exige um buffer com espaço; a função aloca o tamanho certo com mallocO programa gerado não libera essa memória (aceitável para programas curtos)
Tipo de cada parâmetro deduzido pelos argumentos das chamadas (f("oi") → const char *); tipo de retorno deduzido pelos returnTodo parâmetro int (versão anterior) / exigir anotação de tipoPython não declara o tipo dos parâmetros; é a mesma ideia da dedução de tipo das variáveis. Com tudo int, uma string passada como argumento era impressa como númeroOs tipos dependem uns dos outros (retorno ← parâmetros ← argumentos), então a análise roda alguns passos até estabilizar. Tipos incompatíveis no mesmo parâmetro são erro semântico; inteiro e float viram double

04 / QUALIDADE

Testes e processo

DecisãoAlternativa consideradaPor que escolhemosConsequência
Suíte de testes automática: cada teste é entrada.py + esperado.txt, comparados pelo run_tests.shComparação visual da saída (versão inicial)Qualquer mudança que quebre uma etapa aparece na hora como [FALHA] com o diffmake test roda 28 testes; o esperado.txt precisa ser atualizado quando o formato da saída muda de propósito
Testes de geração ponta a ponta: Python → C → gcc → executa → compara a saída do programaComparar o texto do C geradoTesta o que importa (o programa produz o resultado certo) e não quebra com mudanças de formatação do COs testes dependem de ter gcc instalado
Um teste por etapa do compilador (lexer, parser, AST, tabela, geração)Só testes do programa inteiroQuando algo quebra, a categoria que falha mostra em qual etapa está o problemaO test_lexer roda só o lexer, imprimindo um token por linha
